# 小説アキネーター「図書館の司書」機能 仕様書（ドラフト）

> 本ドキュメントは `docs/specification.md`（本体仕様）と `docs/ux_psychology.md`（UX心理学適用ガイド）の延長として、
> 「小説版アキネーター」を実現するための**質問・回答データ収集基盤**と、それを支えるUI「図書館の司書」の仕様を定義する。
> 既存の `stamps` / `charm_tags` / `triage_*` と同じ思想（軽い操作で蓄積、段階的要請、ピーク・エンド演出）で設計する。

---

## 0. ゴールと全体像

### 0.1 やりたいこと

1. **小説 × 質問** ごとの回答を貯める（例:「主人公は最初から強いですか？」→ はい / いいえ …）。
2. 回答は**ユーザーに答えさせる**。小説詳細から「図書館の司書」へ飛び、気軽に答えてもらう。
3. 集まった回答を**小説に紐づけて集計**し、将来のアキネーター（質問で小説を当てる）エンジンの知識ベースにする。

質問文の設計（どんな質問を用意するか）は**別途検討**。本仕様は「質問を入れる箱」「回答を集める導線」「集計の仕組み」を定義する。

### 0.2 アキネーターの原理（なぜこのデータ構造か）

アキネーターは確率モデルである。各 **(対象, 質問)** ペアについて「はい/いいえ/たぶん…」の回答分布を持ち、
ユーザーの回答列から最も整合する対象を推定し、情報利得が高い質問を選ぶ。
したがって本機能の本質は **(novel, question) ごとの回答カウントを群衆から集めること** に尽きる。

```
収集フェーズ（本仕様の主対象）          推定フェーズ（フェーズ2）
ユーザー → 司書UI → 回答(raw)          プレイヤーの回答列
            │                              │
            ▼                              ▼
   novel×question 集計スコア  ───→  ベイズ推定で小説を当てる
```

## 1. データモデル

既存テーブル（`novels`, `bookmarks`, `stamps` 等）を前提に、新規4テーブルを追加する。
命名・スタイルは `20260303000001_triage_stamps_tags.sql` に準拠（`bigint GENERATED BY DEFAULT AS IDENTITY`, `auth.users` 参照, RLS有効化）。

### 1.1 `akinator_questions` — 質問マスター

質問文は別途用意するため、まずは入れ物を定義。システム提供（`is_system=true`）を基本とし、将来的にユーザー投稿質問も許容できる形にしておく。

| カラム | 型 | 制約 | 説明 |
|--------|-----|------|------|
| id | bigint | PK | 内部ID |
| text | text | NOT NULL | 質問全文（司書のセリフ）「主人公は最初から強い？」 |
| short_label | text | | カルテ表示用の短縮ラベル「俺TUEEE度」 |
| category | text | | 分類（`character` / `setting` / `tone` / `plot` / `meta` 等）。出題の偏り防止・分析用 |
| answer_type | text | NOT NULL DEFAULT 'binary5' | 回答UIの種別（後述）。当面 `binary5` のみ |
| polarity | smallint | NOT NULL DEFAULT 1 | スコア化の向き（+1 / -1）。質問文の言い回し反転に対応 |
| weight | real | NOT NULL DEFAULT 1.0 | 推定時の重み（識別力の高い質問を強める。初期は1.0） |
| is_system | boolean | NOT NULL DEFAULT true | システム質問か |
| author_user_id | uuid | FK→auth.users, NULL可 | ユーザー投稿時の作成者 |
| is_active | boolean | NOT NULL DEFAULT true | 出題対象か（不適切質問の停止に使用） |
| sort_order | int | NOT NULL DEFAULT 0 | 表示・出題順の初期値 |
| created_at | timestamptz | NOT NULL DEFAULT now() | |

### 1.2 `akinator_answers` — ユーザー回答（raw）

**1ユーザー・1小説・1質問につき1レコード**。回答は上書き可能（考えが変われば更新）。これが収集の心臓部。

| カラム | 型 | 制約 | 説明 |
|--------|-----|------|------|
| id | bigint | PK | |
| user_id | uuid | FK→auth.users, NOT NULL | 回答者 |
| novel_id | bigint | FK→novels, NOT NULL | 対象小説 |
| question_id | bigint | FK→akinator_questions, NOT NULL | 質問 |
| answer | smallint | NOT NULL | 回答値（-2..+2、下表） |
| confidence | smallint | NOT NULL DEFAULT 2 | 自信度（1=なんとなく,2=普通,3=断言）。将来重み付けに使用。当面固定でも可 |
| created_at | timestamptz | NOT NULL DEFAULT now() | |
| updated_at | timestamptz | NOT NULL DEFAULT now() | |

**ユニーク制約**: `UNIQUE(user_id, novel_id, question_id)` → upsert で回答更新。

**回答値スケール（`binary5` = アキネーター標準の5択）**

| 表示（司書UI） | answer | 集計での意味 |
|----------------|--------|--------------|
| はい | +2 | 強い肯定 |
| たぶんはい | +1 | 弱い肯定 |
| わからない／読んでないとこ | 0 | 中立（集計の分母に含めるが符号0） |
| たぶんいいえ | -1 | 弱い否定 |
| いいえ | -2 | 強い否定 |

> 「わからない」は**スキップとは別**。スキップ＝回答を作らない、わからない＝「判断できない」という情報として記録する。

### 1.3 `akinator_novel_question_stats` — 集計（novel × question）

推定フェーズで高速に引けるよう、回答を**トリガーで集計**して保持する集約テーブル。
（マテビュー＋cronでも可だが、回答即反映・カルテ完成度表示のためトリガー方式を採用）

| カラム | 型 | 制約 | 説明 |
|--------|-----|------|------|
| novel_id | bigint | FK→novels, NOT NULL | |
| question_id | bigint | FK→akinator_questions, NOT NULL | |
| yes_strong | int | DEFAULT 0 | +2 の件数 |
| yes_weak | int | DEFAULT 0 | +1 の件数 |
| unknown | int | DEFAULT 0 | 0 の件数 |
| no_weak | int | DEFAULT 0 | -1 の件数 |
| no_strong | int | DEFAULT 0 | -2 の件数 |
| total | int | DEFAULT 0 | 全回答数（unknown含む） |
| score | real | DEFAULT 0 | 正規化スコア [-1, +1]（下式） |
| updated_at | timestamptz | DEFAULT now() | |

**主キー**: `PRIMARY KEY(novel_id, question_id)`

**score の定義**（unknownを符号0として平均、polarity と将来の信頼補正を反映）

```
raw_mean = Σ(answer) / NULLIF(total, 0) / 2     -- [-1, +1] に正規化
score    = polarity * raw_mean
```

> 少数回答の暴れを抑えたい場合は、ベイズ平均（事前 m 票・平均0で縮約）を採用:
> `score = polarity * (Σanswer/2) / (total + m)`（m=3 程度）。MVPでは単純平均、運用後に切替。

### 1.4 `akinator_answer_reports` — 通報（任意・データ品質用）

荒らし・誤答対策。「この作品にこの回答はおかしい」を集める軽量テーブル。MVPでは後回し可。

| カラム | 型 | 制約 | 説明 |
|--------|-----|------|------|
| id | bigint | PK | |
| reporter_user_id | uuid | FK→auth.users, NOT NULL | |
| novel_id | bigint | FK→novels, NOT NULL | |
| question_id | bigint | FK→akinator_questions, NOT NULL | |
| reason | text | | |
| created_at | timestamptz | DEFAULT now() | |

### 1.5 ER 概略

```
auth.users ──< akinator_answers >── akinator_questions
                    │  (novel_id)
                    ▼
                 novels
                    │
   akinator_novel_question_stats (novel_id, question_id) ← トリガーで集約
```

## 2. 集計トリガー

`akinator_answers` の INSERT / UPDATE / DELETE で `akinator_novel_question_stats` を再計算する。

- INSERT: 該当 (novel, question) 行を upsert し、対応バケット +1、total +1、score 再計算。
- UPDATE（回答変更）: 旧バケット -1 / 新バケット +1、score 再計算。
- DELETE: バケット -1、total -1、score 再計算。

実装方針: バケット±だけだと polarity 変更や端数で誤差が出るため、**該当 (novel, question) を回答テーブルから集計し直す `recompute(novel_id, question_id)` を1関数**にまとめ、トリガーから呼ぶ（行数は1小説×回答済み質問数程度で軽い）。`SECURITY DEFINER` で stats を書き込む。

## 3. 出題ロジック（どの質問を司書に出させるか）

司書セッションで「次に聞く質問」を選ぶ。Postgres RPC（関数）`get_librarian_questions(p_novel_id, p_limit)` を `SECURITY DEFINER` で提供し、RLSを跨いで集計を参照する。

優先順位（スコアの高い順に N 問返す）:

1. **このユーザーが未回答**の質問のみ対象（`akinator_answers` に自分の行が無い）。
2. **データが薄い質問を優先**（その小説で `total` が小さい (novel, question) ＝ 穴埋め）。群衆全体のカバレッジを上げる。
3. `is_active = true` のみ。
4. カテゴリが偏らないよう軽く分散（同カテゴリ連続を避ける）。
5. 同点は `sort_order` → ランダム。

```sql
-- 概念クエリ
SELECT q.*
FROM akinator_questions q
LEFT JOIN akinator_novel_question_stats s
       ON s.question_id = q.id AND s.novel_id = p_novel_id
WHERE q.is_active
  AND NOT EXISTS (
        SELECT 1 FROM akinator_answers a
        WHERE a.user_id = auth.uid()
          AND a.novel_id = p_novel_id
          AND a.question_id = q.id)
ORDER BY COALESCE(s.total, 0) ASC, q.sort_order ASC, random()
LIMIT p_limit;
```

1セッションの出題数は**5問**を既定（`ux_psychology.md`「決断疲れの防止」。Triageの20枚より軽く）。

## 4. UI：図書館の司書

### 4.1 導線（エントリポイント）

小説詳細画面（`lib/screens/novel_detail/novel_detail_screen.dart`）に新セクションを追加。
既存の「スタンプ」「メモ」「タグ」セクションと同じ並びに置く。

```
── 蔵書カルテ ──
📚 この作品、司書に教える
   カルテ完成度 ▓▓▓▓░░░░ 42%   ［答える →］
   ※あなたが答えた: 8問 / みんなの回答: 31件
```

- 完成度 = 「回答が一定数集まった質問数 / 全アクティブ質問数」など、群衆カバレッジの可視化（サンクコスト＆目標勾配）。
- タップで司書セッション（ボトムシート or 全画面）を起動。

### 4.2 司書セッション画面（`lib/screens/librarian/`）

スタンプシート（`lib/screens/stamp/`）に近い、軽量な単問→単問のフロー。

```
┌─────────────────────────────┐
│  📖 図書館の司書              │
│  「転生したらスライム〜」について │
│                             │
│   ┌───────────────────────┐ │
│   │  Q. 主人公は最初から    │ │   ← 司書の吹き出し（質問文）
│   │     強いタイプ？        │ │
│   └───────────────────────┘ │
│                             │
│   [ はい ] [ たぶんはい ]    │   ← binary5。大きめタップ領域
│   [ わからない ]             │
│   [ たぶんいいえ ] [ いいえ ] │
│                             │
│   ［スキップ］   あと 3 問     │   ← ツァイガルニク（残数表示）
└─────────────────────────────┘
```

操作フロー:
1. RPC `get_librarian_questions(novelId, 5)` で5問取得。
2. 1問表示 → タップで回答を**楽観的更新**（即 upsert、待たせない＝ドハティの閾値）。
3. 司書が短いリアクション（変動報酬）。「ふむふむ」「なるほど、メモしました📝」等を回答内容に応じて出し分け。
4. 次の問題へスライド遷移。
5. 5問完了 → **ピーク・エンド演出**：「ありがとう！カルテが◯%埋まりました」達成アニメ＋Haptics。続けるか終了かを提示（「もう5問いく？」）。

### 4.3 司書ペルソナ

- トーン: 丁寧で少しお茶目な図書館司書。圧をかけず「気軽に答えていい」雰囲気。
- わからない/スキップを**肯定的に**受け止める（「無理に答えなくて大丈夫ですよ」）→ データ品質（適当回答抑制）に効く。
- 既存の絵文字スタンプ文化に合わせ、リアクションに絵文字を活用。

### 4.4 段階的要請（既存ux_psychologyとの接続）

- 初回はスタンプ同様、軽いガイドのみ（反応型オンボーディング）。
- スタンプを押した直後に「ついでに司書にも教える？」と**控えめに**提案（L2的な段階的要請）。
- 回答数に応じた控えめバッジ（「司書見習い→司書→主任司書」）。ゲーミフィケーションは控えめに。

## 6. RLS ポリシー

| テーブル | SELECT | INSERT/UPDATE/DELETE |
|----------|--------|----------------------|
| `akinator_questions` | authenticated 全員（`is_active` 問わず読めてよい） | システム管理（ユーザー投稿を許す場合のみ自分の `author_user_id` で INSERT） |
| `akinator_answers` | **自分の行のみ**（他人の生回答は非公開＝プライバシー & 集計バイアス回避） | 自分の行のみ CRUD（`auth.uid() = user_id`） |
| `akinator_novel_question_stats` | authenticated 全員（集計は公開） | 書き込みはトリガー関数（`SECURITY DEFINER`）のみ。直接 INSERT 不可 |
| `akinator_answer_reports` | 自分の通報のみ | 自分の通報を INSERT |

> 集計（stats）は全員が読めるが、誰がどう答えたか（answers生データ）は本人しか見えない。
> これによりカルテの統計表示は可能、かつ個人の回答は秘匿される。

## 7. データ品質・不正対策

| リスク | 対策 |
|--------|------|
| 適当回答・荒らし | 「わからない/スキップOK」の設計で無理回答を減らす。`reports` で通報。集計はベイズ縮約で少数票の暴れを抑制 |
| 未読者の当て推量 | 既定では**誰でも回答可**（軽さ優先）だが、`confidence` と「ブックマーク/既読フラグ」を将来の重みに利用可能（メタ情報として記録） |
| 1人で大量投票 | `UNIQUE(user_id, novel_id, question_id)` で1人1票（上書きのみ） |
| 質問文の不備 | `is_active=false` で即停止。`polarity` 反転で言い回しズレを吸収 |
| 少数小説でデータ枯渇 | カバレッジ優先の出題（§3）で薄い小説・薄い質問を優先的に埋める |

## 9. アキネーター利用のポイント経済（回数制限）

アキネーター（推定プレイ＝フェーズ2）の利用回数を、**ログインボーナス**と**いいねポイント**で実質的に絞る。
無制限プレイによるサーバー負荷・体験の安売りを防ぎ、毎日来る／回答を貯める動機（変動報酬・目標勾配）を作る。

### 9.1 ポイントの種類

「司書ポイント」（仮称、通貨）を1本に統一して管理する。残高の増減で利用可否を判定。

| 入手元 | 付与 | 補足 |
|--------|------|------|
| **ログインボーナス** | 1日1回ログインで +N（例: +3） | 連続ログインでボーナス増（既存UXの変動報酬と整合） |
| **いいねポイント**（回答/カードへの「いいね」） | 自分の回答・布教カードが他者に「いいね」される度に +1 | 良質な回答を貯める動機 → §1の収集を後押し |
| **司書への回答** | 1問回答ごとに +α（少額） | 「答える人ほど遊べる」設計＝収集とプレイの好循環 |

### 9.2 消費

| アクション | 消費 |
|------------|------|
| アキネーター1プレイ開始 | -M（例: -5） |
| （任意）ヒント・もう1問粘る | 追加 -1 |

残高 < M のときはプレイ不可。「明日ログインで回復」「司書に答えると貯まる」を提示（損失回避＋次行動の誘導）。

### 9.3 データモデル

| テーブル | 役割 |
|----------|------|
| `user_points` | `user_id` PK、`balance int`、`updated_at`。現在残高（集計のキャッシュ） |
| `point_transactions` | `id`, `user_id`, `delta int`, `reason text`（`login_bonus`/`answer_reward`/`like_received`/`akinator_play`/`hint` 等）, `ref_id`, `created_at`。**台帳（source of truth）** |
| `answer_likes` | `id`, `liker_user_id`, `target_user_id`, `akinator_answer_id`(or card_id), `created_at`、`UNIQUE(liker, target_ref)` |

- 残高は `point_transactions` の合計だが、毎回SUMせず `user_points.balance` をトリガー/RPCで増減（読み取り高速化）。台帳と突き合わせて監査可能。
- **不正対策**: 付与/消費は必ずサーバー側（Postgres RPC `grant_points` / `spend_points`、`SECURITY DEFINER`）経由。クライアントから直接 `user_points` を書けないようRLSで禁止（SELECTのみ許可）。
- **二重付与防止**: ログインボーナスは「同一日に `login_bonus` 取引が無いこと」を条件に付与（`UNIQUE(user_id, date, reason='login_bonus')` 相当を部分インデックスで担保）。いいねは `answer_likes` のUNIQUEで1回のみ。
- **自己いいね無効**: `liker_user_id <> target_user_id` をチェック制約／RPCで弾く。

### 9.4 RLS

| テーブル | SELECT | 書き込み |
|----------|--------|----------|
| `user_points` | 自分のみ | RPCのみ（直接 INSERT/UPDATE 不可） |
| `point_transactions` | 自分のみ | RPCのみ |
| `answer_likes` | 自分が付けた / 自分が受けた行 | 自分が `liker` の INSERT のみ（自己いいね禁止のCHECK付き） |

### 9.5 UI

- アキネーター入口に残高バッジ（🔖 司書ポイント ×12）。
- プレイ消費時はアニメで減算（労働の錯覚・ユーザー歓喜）。
- 残高不足モーダル: 「明日ログインで+3／司書に5問答えると+5」。CTAで司書セッション（§4）へ直接送客＝収集に還流。

## 10. 要確認事項（プロダクト判断）

1. **回答スケール**: アキネーター標準の5択（はい〜いいえ）を採用。よりカジュアルにするなら3択（はい/わからない/いいえ）も可。
2. **回答できる人の制限**: 既定は「誰でも（軽さ優先）」。「ブックマーク済みのみ」に絞ると質が上がるが回答数が減る。
3. **司書のキャラ性**: 名前・口調・ビジュアル（既存の絵文字スタンプ文化に寄せる想定）。
4. **完成度の定義**: 「一定票数集まった質問の割合」か「自分が答えた割合」か（カルテ表示の意味づけ）。
5. **集計式**: MVPは単純平均、運用後にベイズ縮約へ切替で良いか。
6. **ポイント設定値**: ログインボーナス +3 / 1プレイ -5 / 回答 +α / いいね +1 は仮。1日あたり何プレイ相当にしたいかで再調整。
7. **ポイント名称**: 「司書ポイント」は仮。世界観に合わせて命名。

## 付録: 推定エンジンとAI／チューニング方針

> 補足質問「専用にモデルをチューニングする場合に適したAIと金額感」への設計上の回答。

### A. まず「LLMのファインチューニングは不要」

小説アキネーターの推定は **確率モデル（§1の集計テーブル）そのもの** で動く。
LLMを微調整する必要はなく、むしろ以下が安価・高精度・即時:

| 方式 | 中身 | コスト感 |
|------|------|----------|
| **ベイズ＋情報利得**（推奨） | `akinator_novel_question_stats.score` を尤度に、回答列から各小説の事後確率を更新。次の質問は情報利得（エントロピー減）最大を選ぶ | **追加AIコスト0**。Postgres/Edge Functionの計算のみ。本家アキネーターも同系統 |
| 埋め込み（embeddings）併用 | 自由入力（「こんな小説」）を受ける場合のみ、作品メタを埋め込み検索で候補集合に絞る | 埋め込みは安価（100万トークン単位で数十円〜）。微調整より遥かに安い |

→ **収集データが貯まるほど精度が上がる**設計なので、初期投資としてのチューニングは費用対効果が悪い。まずP1で回答を貯めるのが最優先。

### B. それでも「LLMチューニング」を検討する用途

LLMが効くのは推定本体ではなく周辺タスク（質問文の自動生成、曖昧回答の解釈、司書のセリフ生成）。
ただしこれらも**プロンプト＋数例（few-shot）で十分**で、ファインチューニングはほぼ不要。

### C. チューニング手段と金額感（どうしても独自学習する場合）

| 提供 | 微調整の可否 | 金額感（目安） | 備考 |
|------|--------------|----------------|------|
| **Anthropic / Claude** | 第一者APIでの一般提供なし。Amazon Bedrock 経由で一部モデル（Haiku系）の微調整が限定提供されてきた程度 | 要見積もり。基本はプロンプト設計で対応する想定 | 本アプリは Supabase + 司書UI でClaude APIを**呼ぶだけ**でも十分（質問文生成・セリフ生成）。モデル: `claude-haiku-4-5`（軽量・低単価）/ 高品質生成は `claude-opus-4-8` |
| OpenAI 等 他社 | gpt系で微調整提供あり | 学習: 数百円〜数千円／データ規模次第、推論は割増単価 | 価格は変動するため要確認 |
| OSS（Llama / Qwen 等）+ LoRA | 自前GPU or Together/Fireworks等 | GPU時間課金。小規模LoRAなら数千円〜 | 運用・MLOpsコストが別途かかる |

> 料金は時期で変動。Claudeの最新モデル・単価は本リポジトリで Claude API を使う際に都度確認すること（例: Haiku系=低単価の軽量モデル、Opus系=最高品質）。

### D. 推奨ロードマップ（コスト順）

1. **P1〜P2: AIコスト0** — 集計テーブル＋ベイズ推定だけでアキネーターを成立させる。
2. **必要になったら Claude API をオンデマンド呼び出し** — 質問文の量産・司書のセリフ多様化を `claude-haiku-4-5` で。プロンプト＋few-shotで足り、微調整不要。
3. **大規模化して初めて検討** — 独自微調整は、データと収益が十分育ってから費用対効果を再評価。
